## Full description

```
If you use an iPhone and a Windows PC, you already know the gap. On a Mac, a verification
code arrives and Safari offers to fill it in one click. On Windows, you pick up your phone,
read six digits, and type them.

SMS Code Bridge closes that gap. When a verification code arrives on your iPhone, it appears
in Chrome, ready to fill.

HOW IT WORKS

Nothing is installed on your phone. You add an Apple Shortcut — the standard, built-in
Shortcuts app — and one automation that runs it when a message containing "code" arrives.
The Shortcut pulls the digits out of the message on the phone and sends only those digits to
a small relay, which pushes them to your browser. The extension finds the verification-code
field on the page and offers to fill it.

Setup is a QR code, a Shortcut import, and one automation you create yourself, because Apple
does not allow automations to be distributed. It takes a couple of minutes, once.

WHAT LEAVES YOUR PHONE

The digits. That is all.

The text of your messages never leaves the phone. The Shortcut extracts the code on-device
and sends only the code and your pairing ID. If a message has no code in it, the Shortcut
makes no network request at all — nothing is sent, and the relay never learns the message
existed.

The relay holds a code in memory for the length of one request, pushes it to your browser,
and forgets it. Codes are never written to disk and never logged. There are no accounts, no
email address, no analytics, and no third parties beyond your browser's own push service.

The extension never writes a code to storage. A code lives in memory, expires after 60
seconds, and disappears if the browser restarts. Your pairing ID can be rotated from the
popup at any time, which revokes the old one on the relay immediately.

WHAT IT DOES NOT DO

It is not end-to-end encrypted. Apple's Shortcuts app has no cryptographic actions, so there
is no way to encrypt the code on the phone. Codes are protected by TLS in transit, but the
relay can technically see them for the moment it holds them. We would rather say that plainly
than bury it.

iOS shows a notification every time an automation runs. Apple forces this and it cannot be
turned off, so expect a banner on your phone with each incoming code.

Whether an automation fires reliably while your iPhone is locked depends on your iOS
version, and Apple documents no guarantee. If it does not fire on your phone, the extension
cannot help — and this is the single biggest reason this might not work for you.

The extension and the relay are open source. Everything above can be checked in the code
rather than taken on faith.
```

> If Spike 1 (`docs/SPIKES.md`) lands in the 50–90% band, the "WHAT IT DOES NOT DO" section must
> be amended to say "usually instant, occasionally you tap the notification" *before* submission.
> Do not ship copy that asserts locked-phone reliability the spike has not measured.

Required by Chrome Web Store policy.

```
The single purpose of this extension is to deliver a one-time SMS verification code from the
user's paired iPhone into the verification-code field of the page the user is currently
logging in to.

Every permission, the content script, the relay connection, and the notification fallback
exist solely to move that one code from the phone to that one field. The extension has no
secondary feature: it does not read, store, or transmit page content, it does not manage
passwords or accounts, and it does not function on any page where a verification-code field
is not present.
```

## Permission justifications

The manifest is generated by WXT from `extension/wxt.config.ts` plus the content script's own
`matches`. The complete list of what is requested:

| Permission | Where it is declared | What it is used for | Why the extension cannot work without it |
|---|---|---|---|
| `storage` | `wxt.config.ts` → `permissions` | `chrome.storage.local` holds three values: the pairing ID, the timestamp of the last received code, and the last error string shown in the popup. `chrome.storage.session` holds one value: which tab and frame most recently had a verification-code field focused. | The pairing ID identifies which browser a code belongs to and must survive browser restarts — without it the pairing is lost on every restart and the user must re-pair daily. The session entry is how the extension knows which of several open tabs is waiting for the code; it is memory-backed and never touches disk. **No verification code is ever written to either store.** (`extension/entrypoints/background.ts`) |
| `notifications` | `wxt.config.ts` → `permissions` | The fallback path. If a code arrives and no verification-code field can be found — the user is on a different tab, a `chrome://` page, or a PDF — the extension shows a notification so the code is not silently lost. | Web Push in Chrome requires subscribing with `userVisibleOnly: true`, and beyond that policy point, a code that arrives with nowhere to go must surface somewhere or the user is left staring at a field that never fills, with no way to recover. Losing the code silently is the failure mode this permission exists to prevent. (`notifyFallback` in `background.ts`) |
| `host_permissions`: the single relay origin | `wxt.config.ts` → `host_permissions`, derived from `WXT_RELAY_URL` at build time | The service worker's `fetch` calls to the relay: `POST /pair` to register the push subscription, `DELETE /pair` to revoke it on rotation. | The relay is the only server the extension talks to, and Push cannot work without a server holding the VAPID keys — an MV3 service worker cannot listen on a socket or hold a persistent connection, so a relay is structurally required. This is one exact origin, not a wildcard: `https://*.workers.dev/*` would have granted access to every Cloudflare Worker on the internet, which is far more privilege than the extension needs. |
| Content script on `<all_urls>`, `all_frames: true` | `extension/entrypoints/content.ts` → `matches` | Detecting the verification-code field on the page and filling it, or rendering the suggestion pill next to it. | See below. |

Note what is *not* requested: there is no `tabs` permission (the extension uses only the parts of
`chrome.tabs` available without it), no `activeTab`, no `scripting`, no `clipboardRead`, no
`webRequest`, no `cookies`, and no host permission for any site other than the relay.

### The `<all_urls>` content script — full justification

This is the permission a reviewer should push on, so here is the complete case.

**What it does.** On each page and frame, the content script:

1. Listens for `focusin` and checks whether the focused `<input>` looks like a verification-code
   field, by testing its `autocomplete`, `name`, `id` and `aria-label` attributes.
2. If so, sends the extension a message containing **no data at all** — literally
   `{ type: "otp-field-focused" }` — so the service worker knows which frame to aim at.
3. When a code arrives, locates the field and either fills it (only when the SMS carried an
   origin-bound `@domain #code` sigil matching this frame's origin) or renders a small pill
   showing the code with a *Fill* button.

**What it does not do.** It reads no page text, no form values, no cookies, and no storage. It
makes no network requests of any kind. The only two messages it can send are
`otp-field-focused` and `otp-field-present`, both of which are bare type tags with no payload
(`extension/src/messages.ts`). Nothing about the page — not its URL, not its contents — is ever
transmitted anywhere.

**Why the match pattern cannot be narrowed.** The set of sites that send SMS verification codes
is every site that offers SMS two-factor authentication: banks, carriers, retailers, exchanges,
government portals, airlines, employers' SSO, and every small site using Twilio. There is no
registry of them, no way to enumerate them in advance, and the list grows daily. A user's bank
is exactly the site where this must work, and it is exactly the site we cannot know the name of.

Narrowing to a curated list would mean the extension silently fails on the site the user
actually needs, with no indication why — and the failure would be indistinguishable from the
iPhone automation not firing, which makes it undiagnosable. A permissions prompt per site is not
available either: the code arrives *asynchronously*, seconds after the user has already focused
the field, so there is no user gesture at delivery time to hang an `activeTab`-style grant on.

`activeTab` specifically does not work here for two reasons: it requires a user action on the
extension itself (a click or a shortcut) to grant access, which does not exist in this flow; and
it does not reach subframes reliably.

**Why `all_frames: true` is necessary.** Verification-code fields are frequently inside
cross-origin iframes — Stripe's payment step, embedded bank widgets, SSO flows. A top-frame-only
script cannot see or fill them. It is also a security requirement rather than only a
functionality one: the design fills silently only when an origin-bound code matches the origin,
and that comparison must be made against the **frame's** origin, not the tab's, or a malicious
embedding page could claim an origin it does not own (`docs/DESIGN.md` §8).

**Security measures taken.** The suggestion pill is rendered inside a **closed** shadow root, so
page JavaScript cannot read the code out of the extension's own UI before the user clicks. The
code enters the page's DOM only on an explicit user action, or on the origin-verified silent-fill
path. The extension never overwrites a field that already has a value, and after writing it reads
the value back — a React-controlled input that discards the write causes a fall back to the
manual pill rather than a false claim of success (`shared/src/fields.ts`).

## Notes for the reviewer

**The full flow needs a physical iPhone, which you probably do not have.** The phone half is an
Apple Shortcut the user builds from published instructions, plus a Messages automation. Neither
ships in the extension package. Everything below lets you exercise the extension end to end
without one, by taking the phone's place with a single HTTP request.

**Architecture in one line.** iPhone Shortcut extracts the digits from the SMS → HTTPS POST to a
Cloudflare Worker relay → encrypted Web Push (RFC 8291) to the extension's service worker →
content script fills the field. A relay is structurally unavoidable: an MV3 service worker is
suspended aggressively and cannot hold a connection, so Web Push is the only way to wake it, and
Web Push requires a server holding VAPID keys.

### Testing without an iPhone

1. Install the extension and open its popup. It generates a pairing ID, subscribes to push, and
   registers with the relay. Copy the pairing code shown (format
   `K7QM-3XR9-P2WD-8FNJ-4RTV-QW2X`).

2. Open a page with a verification-code field. Any login step with
   `<input autocomplete="one-time-code">` works; a minimal local page is enough:

   ```html
   <input autocomplete="one-time-code" name="otp" maxlength="6">
   ```

   Click into the field. That focus is what tells the extension which frame to aim at.

3. Take the phone's place with one request. Substitute the relay host given in the submission
   notes and the pairing code from step 1:

   ```sh
   curl -X POST https://<relay-host>/code \
     -H "content-type: application/json" \
     -d '{"pairingId":"K7QM-3XR9-P2WD-8FNJ-4RTV-QW2X","code":"482910"}'
   ```

   Expected: `202 {"ok":true}`. Within about a second, a pill appears at the top right of the
   page showing `482910` with a *Fill* button. Clicking it fills the field.

   This request is byte-for-byte what the Shortcut sends. There is no privileged path.

4. **To see the on-device extraction that the Shortcut performs**, post a full message body
   instead. The relay runs the same reference extractor (`shared/src/otp.ts`) over it:

   ```sh
   curl -X POST https://<relay-host>/code \
     -H "content-type: application/json" \
     -d '{"pairingId":"<your id>","message":"Your verification code is 482910"}'
   ```

   In normal operation this field is never used — the phone does the extraction and sends only
   the digits — but it demonstrates the logic and is what the in-product "test my setup" flow
   uses.

5. **To see the silent-fill path**, add a domain. A code fills without a click only when the SMS
   carried an origin-bound sigil per `draft-wells-origin-bound-one-time-codes` **and** it matches
   the frame's origin:

   ```sh
   curl -X POST https://<relay-host>/code \
     -H "content-type: application/json" \
     -d '{"pairingId":"<your id>","code":"482910","domain":"example.com"}'
   ```

   On `example.com` the field fills silently. On any other host you get the pill plus a warning
   naming both domains, which is the phishing signal. Note that the shipping three-action
   Shortcut does not send `domain`, so in practice today every code takes the click-to-fill path.

6. **Other endpoints:** `GET /health` returns `{"ok":true}`. `GET /setup?p=<pairing id>` is the
   mobile onboarding page the QR points at. `DELETE /pair` with `{"pairingId":"…"}` revokes a
   pairing — the popup's *Rotate pairing code* button calls it.

7. **Negative cases worth checking:** a code sent while no verification-code field is on screen
   produces a desktop notification instead of a pill (the `notifications` justification above);
   a wrong pairing ID returns `404 unknown_pairing`; a malformed one returns
   `400 bad_pairing_id`; more than 20 codes in 60 seconds for one pairing ID returns
   `429 rate_limited`.

### Things a reviewer may reasonably want to confirm

- **No code is ever persisted.** Grep the extension for `chrome.storage` — four call sites, in
  `background.ts` only, writing `pairingId`, `lastCodeAt`, `lastError` and `fillTarget`. No code
  value is among them.
- **The content script exfiltrates nothing.** It contains no `fetch`, no `XMLHttpRequest`, and
  its only outbound messages are two bare type tags.
- **The relay logs nothing.** `relay/src/index.ts` has no logging calls on the code path.
- **Source.** The full source of the extension, the relay, and the Shortcut build specification
  is in the public repository, including the design document explaining every trade-off and the
  accepted risks.
